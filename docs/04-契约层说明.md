## 1. 契约层是什么、不是什么

| 是 | 不是 |
|---|---|
| **项目级资产** —— 不属于前端，也不属于后端（`ADR-0003` 决策 4） | 不是"后端的接口文档"（那会让前端只能照着猜） |
| **机器可读且被门禁校验**（本文 §7） | 不是散文（散文无法拒绝一个错误响应体） |
| 前后端**并行开工**的依据：契约先冻结，两边照着写 | 不是"联调时对一下"的临时清单 |

### 1.1 ★ v2 没有 `api.md`，端点清单的权威在 `docs/02 §6.1`

旧仓的 `api.md` 是**从 FastAPI 应用自动生成**的（并要求与 OpenAPI 保持一致，即"新鲜度关卡"）。**v2 不做代码生成**（`docs/03 §6.2`：少一处"改了 schema 忘了重生成"的漂移面）。因此职责按下面切开：

- **端点与路径的唯一权威**：`docs/02 §6.1` 的路由清单（**24 条 path**，脚本可数）。
- **对象形状的唯一权威**：`contracts/*.schema.json`。schema 描述**对象**，**不描述 URL**。
- 两者的连接由本文 §3 的覆盖表保证 —— **每一条 path 都必须指出它用哪些契约**，这就是"零悬空"（`docs/01` 承诺 12）的机械形式。

### 1.2 无体端点

`POST /api/auth/logout` 是 **204 无响应体**，因此**没有可校验的形状**；它在 §3 里归到 C3（会话语义），并在覆盖表里显式标注"无体"。**"没有形状"必须写出来**，否则下一轮会有人以为漏了。

## 4. 书写约定

**沿用旧仓 `contracts/user.schema.json` 的既有做法**（已核对原文件），逐项写死，避免下一份契约各写各的：

| 项 | 约定 | 为什么 |
|---|---|---|
| 方言 | **JSON Schema draft-07**，`$schema` 必写 | 与搬运件一致；draft-07 的 `additionalProperties` / `propertyNames` / `const` 足够表达本仓的需要 |
| `$id` | `https://probcrew.local/contracts/<name>.schema.json` | 与搬运件一致；跨文件 `$ref` 用相对名（`"$ref": "user.schema.json"`） |
| `title` / `description` | 中文；`description` **必须解释"为什么"**，不只说"是什么" | 旧仓原文就是这个风格（例："本契约用 additionalProperties:false 把这条钉死"）—— 它让下一个人**不敢随手改**，而不是"不敢问" |
| `version` | 每份 schema 带 `version`（`v<主>.<次>`），**只增类变更升次版本** | 破坏性变更走 ADR 且**新文件**（见 §5） |
| `additionalProperties: false` | 在**对外对象**上一律开启 | 它是把纪律变成结构的手段：`user` 用它钉死"不得返回 `password_hash`"、`error.detail` 用它钉死"不得出现 `key`/`token`/`password` 一类键名"、`adminImportRequest` 用它钉死"PII 传不进来" |
| `examples` | **必须能通过本文件的校验** | 旧仓已如此做（`check_contracts.py` §2），v2 写成**硬要求**：写不出可校验示例，说明 schema 或设计有问题 |
| ★ `must_render` | **字段级布尔标注**：`{"type": "string", "must_render": true}` | 它是 `docs/02 §1.6` 的 **R-I** 的落点（"后端发了前端不看等于没发"）。draft-07 忽略未知关键字，因此**不需要**扩展方言；前端冒烟测试据此断言该字段出现在 DOM 里 |
| ★ `x-` 扩展 | **只放机器可读的协议事实**（如 `x-http-status-by-code` · `x-cursor-encoding` · `x-v2-deviations`） | `x-` 不是杂物间：**散文一律写进 `description`**，`x-` 只承载"能被脚本读的东西" |
| 语义权威 | **触发条件与前端行为**在 `docs/02 §6.3`；**字段取值集合**在 schema | 单一权威：schema 管"是什么形状"，设计篇管"什么时候发" |
| ★ **契约描述什么** | **API 视图 + 事件载荷** —— **不描述数据库行** | ★ 2026-09-16 裁定。★ 它解决了两个具体归属：`hint_used_total` **不落列**（由 `COUNT(*)` 派生）⇒ 它天然属于**视图**；而 `user_id` / `answer_normalized` 这类不该对学生侧暴露的字段**不被契约背书**。**数据库行的权威是 `docs/02 §3.2`**（表设计篇），契约不重复它的义务 |
| ★ **`examples` 与规模下界** | 带 `minItems` 下界的根形状，**小于下界的片段放 `x-illustrative-examples`，不放 `examples`** | ★ 两条要求会打架：`examples` 必须能通过自校验，而「题库 ≥ 30 道」这类下界让**示例不可能小**。把片段塞进 `examples` 会让校验红灯，删掉下界又会让 MUST 的规模要求退回散文 ⇒ **分开放**：`examples` 保自校验，`x-illustrative-examples` 保可读性，并标明「片段，不满足下界」 |
| ★ **资产 vs 视图** | **含答案 / 解析 / 解法的资产，必须有独立的「去掉秘密」的视图**；无暴露面的资产可直接复用 | ★ 判断标准是「**这条目里有没有不该给学生看的字段**」，不是「它是资产还是视图」。三个实例：`problem` **另立视图**（资产含 `expected` 与 `solution`）· `dag` / `formula` **直接复用资产条目**（没有秘密）· `types` 的 `framework` **没有公开视图**（它只在提示阶梯与 F17 的拆解里出现） |
| ★ **类型映射** | `INTEGER` 0/1/NULL → **`boolean \| null`** · `TEXT(JSON)` → **数组** · 可空 → **`["T","null"]`** | 否则读者会以为契约写错了：库里 `correct` 是 INTEGER，而接口层是布尔 —— 契约描述的是**视图** |

## 5. 只增不改与兼容规则

**这是契约层的铁律**（沿用旧仓 `contracts/README.md` §二）：

| 变更类型 | 允许？ | 需要做什么 |
|---|---|---|
| 新增枚举值（新 `code` / 新事件类型） | ✅ 兼容 | 加进 schema + 实现 + 变更记录（§6） |
| 给已有对象**新增可选字段** | ✅ 兼容 | 加进 schema，并在 `description` 里注明"v2 新增" |
| 给已有对象**新增必填字段** | ⚠️ 需评估 | 先可选、双写一段时间，再收紧 |
| 改字段名 / 改语义 | ❌ **破坏性** | 走 ADR + 新文件 + 迁移期 + 同步消费方 |
| 删除字段 / 删除枚举值 | ❌ **破坏性** | 同上 |
| 收紧校验（可选→必填、放宽→收窄取值范围） | ❌ **破坏性** | 同上 |

**三条 v2 特有的口径**：

1. ★ **`code` 枚举只增不改**（`docs/03 §6.2`）：前端**按 `code` 分支**，因此**取值集合必须稳定**。废弃的取值**标 `deprecated` 而不删除**。
2. ★ **"语义变更"同样算破坏性** —— 字段名没变但含义变了，**比改名更危险**，因为它不会报错（旧仓 README 原文）。
3. ★ **新仓没有历史包袱**：从未发布过的取值**不进枚举**。已废弃的 `model_unavailable` 因此不在 `error.schema.json` 里 —— 它在 v2 实现之前就被拆成 `model_key_missing` 与 `model_unreachable`，收进枚举只会让前端写出永远走不到的死分支。

## 6. 变更流程

| 步骤 | 谁 | 做什么 |
|---|---|---|
| 1 | 任何人 | 提改动（新增枚举值 / 可选字段可直接提） |
| 2 | **R1（架构/集成）** | **契约的唯一审批人** —— 涉及语义变更或破坏性变更必须经 R1 确认 |
| 3 | 提改动的人 | 破坏性变更：**写一份 ADR**（`docs/adr/`），并说明迁移期 |
| 4 | 提改动的人 | **在 schema 内追加变更记录**：新增用 `x-v2-deviations` 式的增量节，废弃用 `deprecated` 标注（见下） |
| 5 | 提改动的人 | 同步**消费方**（本文 §2 的 consumer 列）与 `docs/07` 的主题登记 |

★ **v2 不另设 `contracts/CHANGELOG.md`**（旧仓的三件套之一）：**变更记录就在契约文件里**（`version` + 增量节 + `deprecated` 标注），历史由 **git log** 承担。理由与"一主题一篇"一致 —— 另设一份 CHANGELOG 就是同一件事的第二处记载（`ADR-0003` 决策 6）。

## 7. 校验口径（★ 实现是 `docs/06` 阶段 B 的动作）

旧仓的 `check_contracts.py` 做七节 46 项。v2 逐节适配如下 —— **本文只规定"校验什么"，不在本轮实现**（负责人已裁定）：

## 9. ★ A3 暴露的缺口登记（本轮只登记，不改已写好的文件）

> 本节是**给负责人的清账**，不是本文的义务。三条都来自"把 `docs/01`–`docs/03` 的要求落到契约上"这个过程 —— 只有落笔写契约时才会显形。

### 缺口 1 · ★ `qa_log` 没有任何读取路径 —— ✅ **已裁定：学生自己可见**（2026-09-16）

- `docs/02 §3.5` 为它建了 `qa_log(user_id, created_at)` 索引，并注明用途是"**我的问答历史**"；
- `docs/02 §3.4` 说它支撑"**F7 的问答侧 · F11 的辅助数据源**"；
- 但 **`docs/02 §6.1` 的 24 条 path 里没有任何端点返回它** —— `me/*` 只有 `wrong` / `progress` / `data` / `notice`；`GET /api/admin/students` 的数据视图明写"逐条查看**作答记录与掌握度计数**"，**不含问答流水**。

⇒ **`qa-log.schema.json` 没有消费者** ⇒ 直接违反承诺 12「契约零悬空」⇒ 它曾被暂缓。

**✅ 裁定（2026-09-16，负责人）：学生自己可见。** 即补一条 `GET /api/me/qa`（"我的问答历史"，走 C2 分页 + C9 流水条目）—— 学生能看见自己的提问历史（与错题本并列），而它正好是 `docs/02 §3.4` 所说的「F7 的**问答侧**」的真实出口。

**★ 连带待办（本轮不做）**：`docs/02 §6.1` 需要**补一行** `GET /api/me/qa`。本轮按约定只改 `docs/04`，因此 §3 的覆盖表把它标成"**待补入**"，而不是把计数悄悄改成 25。**C9 的契约可以写了**（前置已清），排第三批。

### 缺口 2 · `GET /api/health` 的响应形状无处安放

24 条 path 逐条映射时，只有它找不到家。**本轮默认并入 C14**，理由是：health 报告的三项**本地事实**（DB · L1 缓存 · 资产 `rev`）正是 `docs/02 §8-14` 启动校验与注册表要自检的同一套东西。**若负责人更希望它单独成一份，总数会变成 15 份。**

### 缺口 3 · `ADR-0003` 决策 7 的"13 份"与实际 **14 份**

差 1 的来源是本轮裁定新增的 `registry.schema.json`（编排注册 + 工具允许集合，R-Q 的落点）。**`ADR-0003` 正文不改**（历史记录），差值记在 §2。**若要求数字严格为 13**，替代做法是把 C9 `qa-log` 并入 C5 `chat`（"一次答疑的形状，与它落下的流水"）—— 但这样 `docs/01` 附录 A 与 `ADR-0003` 里 `qa-log` 作为独立契约的表述就需要另行对齐。

### 缺口 4 · ★ **F17 的拆解「没有家」—— 而且它不该进题目视图**（2026-09-16 写 `problem.schema.json` 时发现）

`docs/01` F17 要求题目可**结构化拆解**（已知 / 所求 / **适用模型**），且验收是「三段字段非空、可被脚本校验」。但 `docs/02 §6.1` 的 24 条 path 里，**没有任何端点返回拆解**。

**本轮的处理与理由**：**不放进 `problem.schema.json`**。因为「**适用模型**」正是「先给方向」那一级提示的内容 —— 把它挂进题目列表，等于学生一打开题就拿到了 F6 提示阶梯的第一级，**绕过 `docs/01` §5 的伦理约束**（那一条正是「把结论放在过程之后」的执行处）。

**因此**：拆解的形状与 transport **随第四批的 `hint` / `chat` 契约一并落**（它属于"帮助"，不属于"题目列表"）。★ 这条是**写契约才会显形**的：只读文档时，"F17 的字段在哪"看起来只是一个待补的表格行。

### 缺口 5 · **F9 的「上溯」没有端点 —— ✅ 已裁定：前端自己做**

`docs/02 §2.4` 把「上溯」划归 `domain`（纯函数层），但 `docs/02 §6.1` **没有对应端点**。

**裁定（2026-09-16）**：**不为它新增端点，也不新增契约** —— 前端用 `GET /api/knowledge/tree` 的 DAG 数据**自己做反向可达 + 计数**（F9 是 SHOULD，需求只是"集合可显示 + 计数"，而反向可达就是一个 BFS）。★ 理由是一笔**代价账**：为一个小功能新增端点，会让 `docs/02 §6.1` 的计数与 `docs/04 §3` 的覆盖表**与实际实现分叉** —— 而那是文档漂移最经典的起点。★ 服务端 `domain/` 的上溯函数**保留**，供答疑链内部定位薄弱点使用，但它**不对外开端点**。
