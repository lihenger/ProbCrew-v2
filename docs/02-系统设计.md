### 1.3 数据分级（★ 2026-09-16 重构：本表**只管"入仓与否"**这一个维度）

**重构原因**：原表把三个**正交维度**塞进一张表 —— **入仓与否** · **传输去向** · **删除与保留**，于是「外传」被写成与 L0/L1/L2 并列的**一级**。但 `student_qa_log` **同时是 L2 且会外传** —— 一张表表达不了"一物两属性"。现在按维度拆开：**本表管入仓**（§1.3）· **去向与删除见 §1.4** · **出网面见 §1.5**。

| 级 | 内容 | 存放 | 入仓？ | 保留与删除 | 含外传字段？ |
|---|---|---|---|---|---|
| **L0** | 代码、契约、文档、**自制内容资产** | `content/`（顶层，与 `contracts/` 并列）+ 代码目录 | ✅ | git 历史 | ❌ |
| **L1** | **开放许可资源缓存**、模型权重 | `backend/data/corpus/` · `backend/data/models/` | ❌ | 可随时重抓 / 删除 | ❌ |
| **L2** | **学生数据**：账号 · 令牌 · 审计 · 问答流水 · 提示流水 · 作答 · 掌握度 | `backend/data/*.sqlite` | ❌ **结构上不可能入仓** | **四类处置见 §1.4** | ★ **`qa_log` 含提问原文 ⇒ 是**（见 §1.5） |

> ★ **路径是"结构上不可能入仓"这句话的一半**：五类自制资产放**顶层 `content/`**，`backend/data/` 因此成为**纯运行时目录**（只装 L1 与 L2）—— 于是 `.gitignore` 可以对整个目录 **deny-by-default**，而不是靠"精确匹配库文件后缀"（旧仓的写法有个洞：`backend/data/*.sqlite` 里的 `*` **不跨目录**，库文件一旦挪进子目录就悄悄不被忽略）。
> **L2 表的机械识别**：全部使用 `student_` 共同前缀，一条 `LIKE 'student_%'` 即可排除（沿用旧仓数据分级约束）。
> **前缀是数据分级口径，目录是代码归属口径** —— 两者严格分开，因此把存储层拆到 `identity/` 与 `learning/` **不会**破坏这条安全属性（ADR-0003 §5）。

**L1 语料的形状（必须约定，否则 F10 不可断言）**：
"语料不入仓"**不等于**"语料没有形状"。最小约定：

```
backend/data/corpus/<教材>/ch<nn>/sec<nn>.md     ← 路径即章节位置
    文件前置元数据（YAML front matter）：
        cite_id:    <教材>-<nn>-<nn>    ← ★ 出处的机器可读标识（F10 的验收对象）
        title:      第 3 章 条件概率
        chapter:    3
        license:    CC-BY-4.0           ← ★ 必填：只收开放许可
        source_url: https://...         ← ★ 必填：来源可追溯
        fetched_at: 2026-09-16          ← ★ 必填：抓取时间
```

- **`cite_id` 是 F10 的验收对象**：检索响应必须带 `cite_id`，而不是一段自由文本的"出处" —— 否则"检索命中带出处"无法断言、也无法核对。
- ★ **只取开放许可资源**（MIT OCW / OpenStax / 可汗学院等），`license` / `source_url` / `fetched_at` **缺一即为资产错误 ⇒ 启动报错退出**（与 §8-14 同一模式）。
- **预抓 + 运行期只读缓存**：抓取在预抓阶段完成，运行期不联网取语料 —— 这样 `cite_id` 长期可复核（网页会变，缓存不会）。
- 缓存缺失时检索**如实说明"出处暂不可用"**（F10），**不得编造章节号**；并计入 §8 的失败模式。

### 1.4 数据存放分工表（★ 2026-09-16 新增 —— "什么存在哪里"的权威表）

**先定义参照物**（"本地"有三个意思，必须分开；此前**从未定义参照物**）：

| 名称 | 指什么 |
|---|---|
| **浏览器本地** | 学生**自己的设备**（`localStorage` / 内存 / HTTP 缓存） |
| **部署主机** | 跑 FastAPI + SQLite 的那台机器。**单机形态 = 教师 / 答辩本人的机器；远程托管形态 = 我们运营的服务器** |
| **第三方** | 用户配置的**远程**模型服务 |

> ★ **必须写死的一句话**：**"不外传"的准确含义是"不发往第三方模型服务"，不等于"数据不出学生设备"。**
> 单机形态下两者重合；**远程托管形态下两者不重合** —— 学生数据**存在我们的服务器上**（这正是 **N17 受控托管**存在的理由）。这是答辩现场最容易被追问的一处。

| 数据 | 存在哪 | 具体位置 / 字段 | 清除动作 | 需求 |
|---|---|---|---|---|
| 会话令牌（明文） | 浏览器本地 | `localStorage`；库里只存 sha256 | 登出 / 401 / 改密 / 禁用 / 删除 ⇒ 清 | F15 · N6 |
| **模型凭据（明文）** | 浏览器本地 | `localStorage`，固定键名，与账号绑定；**服务端不落任何介质** | 登出 / **切换账号** / 删除账号 / 改密 / 手动 ⇒ 清 | **N14** |
| **端点配置**（provider · model · base_url · egress） | 浏览器本地 | `localStorage`，与凭据同生命周期 | 同凭据 | **N16** |
| 界面位置（题目 / 提示层级 / 筛选 / 翻页） | URL | `#/practice?kc=&item=&hint=` | 不适用 | N11 |
| 跨页面临时态（当前 run、未提交作答） | 浏览器内存 | `core/store` | 刷新即丢（可接受） | — |
| 静态资源（katex 等） | 浏览器 HTTP 缓存 | 部署主机静态托管 | 浏览器自清 | N4 |
| 账号 · 令牌哈希 · 审计 · 问答流水（含提问原文）· 提示流水 · 作答 · 掌握度 | **部署主机 · SQLite** | `backend/data/*.sqlite`（七张 `student_` 表） | **四类处置**：四张数据表**硬删** / `token` **级联删** / `user` **脱敏** / `audit` **保留（只记 ID 与动作）** | F16 · F7 · F15 |
| **告知已读标记** | **部署主机 · SQLite** | `student_user.notice_ack_at`（存服务端的理由：**换设备仍须告知**） | 随账号脱敏清空 | **N15** |
| 开放许可资源缓存 · 模型权重 | 部署主机 · 文件系统 | `backend/data/corpus/` · `models/`（不入仓） | 可随时重抓 / 删除 | F10 |
| **运行日志** | **部署主机 · 文件系统** | **`backend/data/logs/`**，轮转 10MB × 5；**内容受 R-O 约束** | 轮转覆盖 | N14 · N16 |
| 契约 · 五类内容资产 · 代码 · 文档 | 仓库 | `contracts/` · `content/` · `backend/` · `docs/` | git 历史 | F20 |
| **提问原文 + 上下文**（仅 P2 远程端点） | **第三方**（不在我们控制内） | 随请求发往远程端点；`qa_log` 只记 `provider` / `model` / `egress` | **删不掉** —— 须与 N15 一并告知 | **N15 · N16** |

**表后三条规则**：

1. ★ **R-O · 日志与审计只记 ID 与动作，不记内容**：不得出现提问原文、学生答案、教材片段、凭据。**理由**：F16 靠"读回 0 行"验收，而**日志文件不在读回清单里** —— 内容一旦进日志，"删除"就只删了数据库那一份。这是原设计里**唯一一个"验收通过但数据仍在"的洞**。
2. **日志目录定死为 `backend/data/logs/`**（此前全仓无日志位置），落在 `backend/data/` 的 deny-by-default 之内，`.gitignore` 既有规则即可覆盖。
3. **凭据与端点配置同生命周期**；**凭据不随令牌撤销而失效**（它是用户的额度，不是我们的会话），但**登出必须清除**（保护"下一个人"）。

### 1.6 检查规则总表（"谁守"必须落在一处）

A1 的 §8 定了 R-A/R-B/R-C 三条规则，本篇的 §7.3 / §7.4 / §8 又散着若干条"可被脚本守住"的断言。**散着写就等于没有** —— 下表把它们收在一处，并明确每条是**可自动**还是**仅 review**。

| 规则 | 内容 | 检查方式 | 谁执行 |
|---|---|---|---|
| **R-A** | 请求体字符串字段必须有上界；判定正则禁嵌套量词 | **可自动**：`scripts/verify.sh` 静态扫描 + 长度/长数字串用例 | 门禁 |
| **R-B** | 写库必须显式 `commit()`；测试必须读回断言 | **可自动**：扫描 + 读回用例 | 门禁 |
| **R-C** | F20 与编排层各须有责任人 | **仅 review**（脚本查不了） | `docs/05` 责任人表 |
| **R-D** | 样式**禁止硬编码颜色/圆角/阴影**，只能来自 `tokens.css` | **可自动**：grep 形如 `#rrggbb` / `rgb(` 的值（§7.3） | 门禁 |
| **R-E** | 前端**不得用 `innerHTML` 拼用户内容** | **可自动**：grep `innerHTML` 赋值（§7.4，XSS 的唯一防线） | 门禁 |
| **R-F** | 可访问性**三项分开**：点击目标 ≥ 32px（可自动）· 键盘可达 + 语义标签（可自动）· **对比度 ≥ 4.5:1（只对"声明的色对"可自动；渲染结果仅 review）** | **可自动**：①② 前端冒烟断言；③ 色对清单 + 纯 Python WCAG 计算（§7.3） | 门禁 |
| **R-G** | URL 必须可寻址，且 `hashchange` / `popstate` 有监听 | **可自动**：路由冒烟（N11） | 门禁 |
| **R-H** | 演示类页面总行数 ≤ 产品功能页总行数 | **可自动**：按 feature 分组统计行数（`docs/01` 承诺 10） | 门禁（review 级） |
| **R-I** | 契约中标记 **`must_render: true`** 的字段，前端**必须实际渲染** | **可自动**：前端冒烟断言该字段出现在 DOM 中 | 门禁 |
| **R-J** | **凭据不得出现在日志 / 审计 / 错误信息 / L2** | **可自动**：grep 日志与审计写入点 + 一条"带凭据请求不产生含凭据日志"的用例 | 门禁 |

> **R-I 的由来**：`docs/01` F3 的验收原文是"前端渲染该标签（**后端发了前端不看等于没发**）" —— 这句话此前**没有载体**。R-I 给它装上了：契约里标 `must_render`，前端冒烟就必须断言它出现在 DOM 里。同理覆盖 F14 / F18 的渲染口径。
> **R-J 是本轮新增风险（N14 连带）的防线**：凭据只存浏览器、随请求传，因此它**会出现在请求头里** —— 任何一处"顺手把整个请求打日志"的代码都会泄露用户额度。
> **R-K…R-O（2026-09-16 新增）** 是"数据走向"重构的执行载体：**R-K** 把出网收口到 `tools/llm.py`（唯一口）· **R-L** 守住载荷白名单 · **R-M** 把 R-J 从四面扩到**七面** · **R-N** 保证"去向可查"不是一句声明 · ★ **R-O 是那个"验收通过但数据仍在"的洞的堵法** —— F16 靠"读回 0 行"验收，而**日志文件不在读回清单里**：内容一旦进日志，"删除"就只删了数据库那一份。

> **R-E 的定位要说清**：它是**唯一**的 XSS 防线，而且**是纪律不是机制**（没有 CSP、没有 DOMPurify —— ★ 理由是"**免构建 + 零依赖**"，而**不是**"离线"；"离线"已不是 v2 的需求口径）。grep 能挡住"顺手写了 `innerHTML`"，挡不住"用 `insertAdjacentHTML` 绕过" —— 这一条仍需要在 review 里看。
> **R-C 是唯一查不了的一条**，正因如此它才必须写进 `docs/05` 的责任人表（`docs/01 §8` 的 R-C 原文）。

### 2.1 名词与职责

| **题目**（Problem） | 题干 + 标准答案 + 知识点标注 + 题型 + 难度 | **内容资产** | F20 |
| **错因模式**（MistakePattern） | 一种可枚举的错误，如"方向颠倒" | **内容资产** | F20（F5 吃它） |

| **作答**（Attempt） | 一次提交：答案、对错、知识点、用时、提示次数 | `learning` | 学生提交 → 判定 |

                  │

        ▼                   ▼
  ┌──────────┐        ┌──────────┐

  └────┬─────┘        └────┬─────┘
       │                   │

                                 ▼
                            ┌──────────┐

```

（示意图；**规模与真实节点以内容资产为准**，首版目标见 F20 的 DAG 要求。）

**四条设计规则**：

1. **ID 稳定且可引用、不得复用** —— 被历史记录长期引用的 ID 一律适用此规则，**不只知识点**：
   - `kc_<slug>`（知识点，如 `kc_bayes`）
   - `prob_<slug>`（题目，被 `attempt.item_id` 引用）
   - `pt_<slug>`（题型，被题目与 F17 的 `model_id` 引用）
   改含义只能**新增 ID** + 把旧的标 `deprecated`，否则历史作答的标注会指向**错误含义**（而且无法事后区分哪些是错的）。
2. **无环是硬约束**（F19 验收）：建图时做拓扑排序，有环即拒绝加载（不是警告）。加载失败必须**报错退出**，不得静默丢边。
3. **边有含义**：`depends_on`（前置）单向。上溯（F9）沿 `depends_on` 反向走。
4. **题目与题型都挂知识点**，但两者独立：一道题可以考多个知识点；一个题型可以服务多个知识点。

### 2.4 领域层的边界（这条决定了可测性）

`domain/` 是**纯函数层**：不碰数据库、不碰 FastAPI、不碰 LangGraph、不发网络请求。

| 属于 `domain` | 不属于 `domain` |
|---|---|
| 分布计算与性质推导（SymPy） | 读写 `student_attempt` |
| 判定规则与归一化（答案比对、等价性） | 调用检索 / 调用模型 |
| 知识点 DAG 的加载与拓扑排序、上溯 | 生成 SSE 事件 |
| 错因匹配（吃错因库） | 权限判断 |
| 题型的解法框架结构 | 页面渲染 |

**理由**：判定是 N1 的地基，而 N1 的验收要求"**注入 20 道已知错解必被发现**"。纯函数层可以**脱离服务、脱离数据库、脱离模型**直接跑注入集 —— 这是让 N1 的验收成本从"起服务跑端到端"降到"跑一个函数"的唯一办法。

> ✅ **已裁定（2026-09-16，负责人）· `student_audit` 在删除用户时保留**
> **设计**：`student_audit` **不随删除而清除**，理由：它是"管理员看过谁的数据"的合规证据，删掉它等于删掉监督记录；且账号本身是**化名**（N6 不采集学号/姓名），脱敏后 `user_id` 已无法回溯到具体的人。
> **同时要求**：删除动作本身必须写一条审计（谁删的、删了几行）。
> **已考虑并否决的替代方案**：① 删除时一并清除 `target_id` 指向该用户的行 —— 否决，因为"该生数据曾被反复查看"这件事会变得不可查，而它恰恰是监督的价值所在；② 对 `target_id` 做盐化 —— 否决，为一条本地部署的审计记录引入一个密钥管理面不划算。
> **代价（记账）**：删除后仍存在"某个匿名 ID 曾被查看过"的记录。这是**有意选择合规证据优先于彻底清除**，若日后合规要求变化，改法是上面被否决的方案 ①。

| `kc_ids` | TEXT(JSON) | **非空强制**（见下） | **F19** |

> **`deleted`（软删）字段已删除**。它原是旧仓搬来的字段，但实测**没有任何代码把它置 1**，而所有读查询都过滤 `deleted=0` —— 是个"**有读无写的死字段**"：既支撑不了 F16（F16 是硬删 + 读回 0 行），也没有任何需求要求它。按附录 A 规则 1，只有"删"或"补需求"两种状态，**本仓选择删**（v2 是新库，无迁移负担）。删后读查询不再需要 `deleted=0` 过滤。若将来要做"撤回误删"，须先补一条需求再加字段。

**新增 `asset_version` 的理由与合规性**：
F7 要求"**标准答案快照 + 资产版本号**"。`expected` 已提供快照，但快照离了版本号**无法解释**——题库改版后，"当时的标准答案"为什么是这个值、知识点标注依据的是哪一版 DAG，都查不出来。
**这是"只增不改"允许的增量变更**：新字段可空、有默认值、不改变任何既有字段的含义，旧数据读出来是 NULL 而非错误。

**`kc_ids` 非空的实现路径（F19）**：
不是"在写入时校验一下"这么弱 —— 而是**从源头保证**：F20 要求**题库条目必须关联知识点 ID**，而 `attempt.kc_ids` 由题目继承。因此：

```
题库条目 kc_ids 必填（F20）
        └─▶ 作答时继承 kc_ids
                └─▶ attempt.kc_ids 天然非空（F19）
```

三层都要有断言：① 题库加载时校验条目 `kc_ids` 非空；② 契约里 `kc_ids` 标 `minItems: 1`；③ 写入函数拒绝空数组并抛错（**不得静默写 `[]`**）。
> 为什么强调第三层：旧仓该列是 `NOT NULL DEFAULT '[]'` —— **"非空"在数据库层面看起来被满足了，实际存的是空数组**。这正是 F19 要防的那种"表面合规"。

#### `student_mastery` —— 聚合口径

| 字段 | 说明 |
|---|---|
| `user_id` + `topic`（PK） | `topic` **就是知识点 ID**（与 `attempt.kc_ids` 同口径，不再另设一套命名） |
| `attempts` / `correct` | 聚合计数 |
| `updated_at` | 最后更新时刻 |

**更新时机**：**每次作答后累加**（同事务）；**`correct` 为 NULL 的作答（不可判定）不累加**。
**不做**"重算全表"——重算会在删除时产生漂移。

**★ 多知识点聚合口径（必须写死，否则数字会虚高）**：一道题可以挂多个 `kc_ids`，一次作答会对**所有** topic 各累加一次 `attempts` / `correct`。因此：

- **进度视图的"总作答数"必须按 attempt 去重**（`COUNT(DISTINCT attempt_id)`），**不得对 `mastery.attempts` 求和** —— 否则同一份作答被重复计入，总量虚高；
- **"首次正确率"的单位是 `(user, item)` 的第一次 attempt**，不是 `(user, topic)` 的第一次 —— 后者在一题多知识点时无定义。

**已知限制（诚实）**：当前口径是**计数**，不含"提示次数对掌握度的扣减"。F6 要求如实记录，但**掌握度公式本身不在 v2 范围内**（属学习者建模，§9 不做）。数据齐备，公式后补 —— 这正是"现在开始记"的意义。

#### 其余几张表
`student_user` / `student_token` / `student_qa_log` / `student_hint_log` 的字段沿用已落地实现（`student_hint_log` 为 v2 新增，字段见 §3.1）；`student_audit` 同理。**字段级机器可读定义在 `contracts/`（A3）**，本篇只记录**本仓的增量**（`asset_version` · `correct` 可空 · `grader` 新增取值）与口径说明。

### 3.3 内容资产：五类、格式与版本化（F20）

| 资产 | 最小规模（首版**下界**） | 必须关联 | 主要消费方 |
|---|---|---|---|
| 题库 | **≥ 30 道**（长期目标 ≥ 100 道，与评测资产共用） | 知识点 ID · 题型 ID · **`gradable` 标记** | 刷题 · 评测 |
| 错因库 | **≥ 40 条** | 知识点 ID | F5 错因诊断 |
| 知识点 DAG | **≥ 40 节点且覆盖 ≥ 5 章**，拓扑无环 | —（节点即 ID） | F9 · F19 · 上溯 |
| 公式库 | — | 知识点 ID | F18 精准检索 |
| 题型与解法套路 | **≥ 15 类** | 知识点 ID | **F17 的"适用模型"** |

四条规模下界都是**下界，只许上调**（与地板阈值同一精神）。

**存放路径（唯一）**：`content/<asset>.json` —— **顶层目录，与 `contracts/` 并列**。理由：五类资产是**项目级真相**（自制、入仓、可 diff、可 review），而 `backend/data/` 从此是**纯运行时目录**（只装 L1 语料与 L2 库）。把"必须入仓"的东西放进"绝不能入仓"的目录里，会让 §1.3 那句"结构上不可能入仓"变得难以一眼自证。

**统一版本化规则**：

1. 每类资产一个文件（或一个目录 + 索引），**文件头带 `rev`**：`<asset>-<YYYY.MM.DD>.<n>`。
2. 生成物 **`content/MANIFEST.json`（入仓）** 记录**五类资产各自的 rev**，并派生出**组合版本号** `content_rev`（五者 rev 的确定性拼接）。
3. `attempt.asset_version` 存**当时的 `content_rev`**；**反解链**：`content_rev` → 同提交的 `content/MANIFEST.json` → 五类资产各自的 `rev` → **`git log` 里升该 rev 的那次提交**（内容与解释一并可查）。
   > 反解**依赖 MANIFEST 入仓 + git 历史**这两件事同时成立。若 MANIFEST 不入仓，旧 `content_rev` 就是一个无法解释的数字 —— 那正是 F7 要防的事。
4. **`rev` 变更即视为内容变更**：改一个错因解释也要升 `rev`。**不允许原地改内容不升版本** —— 否则历史记录的解释链断裂。
5. **一致性由启动校验守住**：资产文件头 `rev` 与 MANIFEST 不一致 ⇒ **启动报错退出**（与 §8 第 14 条同一模式），防止"手改了资产忘了重生成 MANIFEST"静默产出错版记录。

> 资产**入仓**（L0，自制、可版本化、可 diff、可 review）；**教材语料不入仓**（L1，见 §1.3）。
> 这与 N3 不冲突：入仓的是我们自编的题目、错因、DAG、公式、题型；从教材摘录的原文属 L1。

### 3.6 并发与事务（R-B 的落地）

| 规则 | 做法 | 为什么 |
|---|---|---|
| 并发写 | 开启 **WAL** + `busy_timeout=5000` | 读写不互相阻塞；短时争用自动重试而非立即报错 |

## 4. 三条主链路

### 4.1 登录与令牌链路（F15 · N6）

```
浏览器                        后端                         SQLite(L2)
  │                            │                              │
  │ POST /api/auth/login       │                              │
  │ {username, password}       │                              │
  ├───────────────────────────▶│                              │
  │                            │ ① 查 user                    │
  │                            ├─────────────────────────────▶│
  │                            │ ② 不存在 / 已删除 / 空哈希？  │
  │                            │    ⇒ burn_time() + 401       │
  │                            │ ③ bcrypt.checkpw             │
  │                            │    失败 → failed_count+1     │
  │                            │    达上限 → 置 locked_until  │
  │                            │    且**校验失败也烧时间**     │
  │                            │    ⇒ 401（或 423，见下）      │
  │                            │ ★ ④ 锁定中？→ 423            │
  │                            │ ★ ⑤ status=disabled？→ 403   │
  │                            │ ⑥ secrets.token_urlsafe(32)  │
  │                            │    库里只存 sha256(明文)      │
  │                            ├─────────────────────────────▶│
  │ {token, expires_at, user}  │◀─────────────────────────────┤
  │◀───────────────────────────┤                              │
  │                            │                              │
  │ 后续请求：Authorization: Bearer <token>                    │
  ├───────────────────────────▶│ resolve_token(sha256)        │
  │                            │ → revoked/过期/账号禁用 ⇒ 401/403
```

> ★ **③④⑤ 的次序是刻意的**：**锁定与禁用的判定都在密码验证之后**。
> 反例（旧仓实测的次序）：把"锁定中 → 423"放在验证**之前**，则"不存在的用户名"给 `401`、而"已锁定账号"给 `423` —— **无需密码即可区分**，构成账号存在性枚举面。旧仓的禁用检查本就在验证之后（这点是对的），是本篇先前把图画错了，已按实现改正。

**七条口径（每条都对应一个具体的坏结果）**：

| # | 口径 | 不做会怎样 |
|---|---|---|
| 1 | **服务端会话令牌，不是 JWT** | JWT 无状态 → 无法满足"停用账号**立刻**生效" |
| 2 | 库里**只存 sha256**，明文只在登录响应出现一次 | 库被拿走等于所有会话被劫持 |
| 3 | 令牌 **7 天**有效，可即时撤销（`revoked`） | 无法响应"这孩子手机丢了" |
| 4 | **改密码 / 禁用 / 删除 ⇒ 撤销该用户全部令牌** | 改完密码旧令牌还能用，等于没改 |
| 5 | 失败 **5 次锁 60 秒**；**校验失败也烧固定时间** | ① 可无限爆破 ② 通过响应时间可枚举用户名是否存在 |
| 6 | 除 `health` / `login` / 静态资源外，**全部端点要求登录** | **A1 已裁决：不设免登录例外**（理由见 `docs/01` §1） |
| 7 | 管理员账号**只能由 CLI 创建**，接口不可创建管理员 | 否则拿到一个管理员令牌就能自我复制 |

> ★ **信息量不变量（可断言）**：**在密码通过之前，一切失败都返回同一个 `401 bad_credentials`，且都烧等长的时间。**
> 因此"账号已被禁用（403）""尝试次数过多（423）"这两个可区分的状态，**只可能在密码验证通过之后出现**。这条不变量是 §6.3 两个 `code` 拆分成立的前提，也是它唯一的正当性依据 —— 测试直接断言它。

### 4.2 答疑链路（SSE · F1 F2 F3 F10 F13）

```
POST /api/chat  { query, context }        ← 必须登录（F15）
   │
   ├─ ① 校验：query 长度上界（R-A）· context 可缺省但显式降级（F1）
   ├─ ② 落 qa_log（提问原文，L2）—— 先落再答，保证"问了就算数"
   │
   ▼  graph（LangGraph 图运行时）
   ├─ 路由 → 意图（solve / explain / lookup / visualize）
   ├─ 检索（本地语料）→ 命中带出处；**无命中如实说明**（F10 · N2）
   ├─ 求解 → 逐步过程，每步 {说明, 式子}（F2 结构断言，**仅 solve 类**）
   ├─ 验证 → **验证报告**（级别 A–D + 逐项检查 + 置信度）—— 每条解答必带（F3）
   │      ├─ 通过 → 正常输出
   │      └─ ★ **不通过** → 重算一次（**上限 1 次**）
   │             ├─ 重算后通过 → 正常输出
   │             └─ 仍不通过 → **标 `uncertain`** + 级别降 **D** + 事件流**显式告知**
   │                             （附"哪一项检查没通过"）—— **不静默输出，也不假装通过**
   ├─ 需要人协同？→ hitl.request（挂起，等前端确认）
   └─ 汇总 → 事件流
   │
   ▼ SSE 帧（`events.schema.json`）
   │   frame: { seq, type, ts, payload }   seq 单调递增
   ▼
前端消费：seq 去重 · 按类型渲染 · **断流后重新发起（见硬性设计 1）** · 不重放已渲染帧
```

**七条硬性设计**：

1. ★ **`seq` 只用于去重，不承担"断流续传"（2026-09-16 修正）** —— 服务端**不做重放缓冲**，断流语义为"**重新发起（会重跑一次图）**"。**已记账：因此不能续传**。理由：内存环形缓冲在单 worker 下能工作，但要为"断流"引入一套会话态生命周期，而 v2 的 SSE 是**短连接**（一次答疑一次流），收益与复杂度不成比例。若将来改做缓冲，须走 ADR。
2. **客户端断开 ⇒ 图必须取消**。否则一次刷新页面会留下一个还在跑的后台图，把单 worker 拖死。
3. **验证报告缺失即不出结果**（F3："无标签不出结果"）—— 这是 N2 的机制，不是前端的事。
4. ★ **验证不通过有明确出口**（本轮补齐）：**重算一次（上限 1 次）→ 仍不通过就标 `uncertain` 并降级到 D ＋ 显式告知**。
   这是 **N1 的机制所在** —— N1 的验收是"注入的已知错解被拦住或标注"，而"拦住"就发生在这一步。没有这一条，N1 只是一句指标，没有对应设计。
   ★ **"重算"的语义已写死**：**换一条策略重新求解**（多路求解的第二次尝试），**不是**同一次调用的重试采样 —— 同一次调用的多个样本会共享同一个错误前提。上限为 1 次：无限重算会把"验证"退化成"直到算对为止"。**"哪些检查项的什么结果算不通过"见 §4.4 的判定表。**
5. **`hitl.request` / `hitl.resolved` 必须成对**，且前端必须有可见的挂起态 —— 否则用户面对一个永远不动的进度条。
6. **上下文来源可替换**（N12）：`context` 是一个**显式可选参数**，不是"从浏览器读屏"。将来探针接入时，它只是换一个来源，**契约不变**。
7. ★ **F2 的结构断言有明确落点（本轮补齐）**：解答步骤以 **`steps[]`** 出现在两处 —— ① SSE 的解答事件（`events.schema.json` 里承载步骤数组的那个字段）② **`GET /api/runs/{id}` 的响应**（`steps: [{说明, 式子}]`）。**断言的对象是这两处**，不是"事件流里大概有步骤"。仅约束 **solve 类**解答（`explain` / `lookup` 不受"步骤数 ≥ 3"约束）。

### 4.2.1 答疑的前置条件（N14 —— 无凭据则不可用）

```
有凭据 → 走上面的链路
无凭据 / 凭据失效 → ★ 直接返回 503 `model_unavailable`（或 400 `model_key_invalid` /
                      402 `model_quota_exceeded`，见 §6.3），**不发起、不降级、不产出假答案**
                     → 判定 / 错题本 / 进度 / 知识图谱**全部照常可用**（它们不依赖模型）
```

> **为什么连 mock 都不留**：旧仓的 `llm_provider = "auto"`（无 key 走 mock，保证零配置可跑）是**产品模式**，与 **N2 诚实**直接冲突 —— mock 产出的是**假答案**。v2 只在**测试**里注入假 provider，**不提供产品级 mock**。这条要写死，否则会有人把 mock 重新加回来。
> **凭据怎么传**：请求头 `X-Model-Key`（**不放 body**，避免进 body 日志）；因此答疑**必须用 `POST + fetch 流`** —— `EventSource` **不能带自定义头**。若将来改用 `EventSource`，凭据必须改走 cookie 或 body（已列为失败模式，见 §8）。

```

## 5. 状态机

### 5.1 编排图状态机

```
idle ──▶ routing ──▶ running ──┬──▶ verifying ──┬──▶ done
                      ▲         │                │
                      │         │                └──▶ needs_human ──▶ hitl
                      │         │                                    │
                      └─────────┴──◀──────── resolved ◀──────────────┘
                                │
                                └──▶ failed（错误体见 §6.2）
```

**约束**：`done` / `failed` 为终态；`needs_human` **必须有超时**（否则图永远挂着）。
**已知限制（诚实）**：图检查点当前为**内存态** ⇒ **只允许单 worker**。见 §8 的失败模式表。

### 5.2 提示阶梯状态机（F6 —— 伦理约束的落地点）

```
        未作答
          │ 请求提示 1
          ▼
    hint_used=1 ──「方向」**不给完整思路**
          │ 请求提示 2
          ▼
    hint_used=2 ──「步骤骨架」**不给最终答案**
          │ 提交作答
          ▼
        已提交 ──▶ 此时才允许返回**完整解析**
          │ 错题重做（source=wrong_review）
          ▼
        重新作答（attempt_no+1，hint_used **重新计**）
```

**三条不可违反**：① 未提交前**不返回完整解析**；② 每次提示**精确 +1**（这是"如实记入掌握度"的依据）；③ 重做时 `hint_used` 重新计，但**历史不清零**（否则"我第三次才做对"的证据就没了）。

### 5.3 账号状态机（F15）

```
          创建(CLI)              禁用(管理员)
   (无) ──────────▶ active ◀───────────────▶ disabled
                     │  ▲                        │
        删除(本人/管理员) │  │ 启用(管理员)          │
                     ▼  │                        │
                  deleted ◀───────────────────────┘

   任一状态下的失败计数：failed_count≥5 ⇒ locked_until 置未来时刻（60s 后自动解除）
```

**`deleted` 是脱敏态，不是物理删除**：`username` 改为 `deleted_<8hex>`、`password_hash` 置空串（**任何密码都登不进去**）、令牌全撤；**四张学习表**（问答流水 / 提示流水 / 作答 / 掌握度）的数据**硬删**。

> **两个 `deleted` 不再同名易混**：`student_user.status = 'deleted'` 是**账号状态**（保留，脱敏态）；`student_attempt` 的软删字段**已删除**（见 §3.2 —— 它是"有读无写的死字段"）。
>
> **username 复用规则**：脱敏后原 username **可以再次被注册**（不引入"退休用户名表"），因为 `user_id` 不复用；**教师视角靠 `user_id` 后 8 位区分同名**（管理页必须显示它）。若将来发现"同名不同人"造成实际混淆，再改为禁止复用并走 ADR。

### 5.4 令牌状态机

```
issued ──▶ active ──┬──▶ expired（到期）
                    ├──▶ revoked（改密 / 禁用 / 删除 / 主动登出）
                    └──▶ orphan（账号被删除后，行被级联清理）
```

## 6. 接口与错误语义

### 6.1 路由清单（按模块）

| 模块 | 端点 | 认证 | 备注 |
|---|---|---|---|
| 系统 | `GET /api/health` | **否** | 唯一无需登录的 API；报告 DB / 模型 / 检索状态 |
| 身份 | `POST /api/auth/login` | 否 | 唯一另一个例外 |
| 身份 | `POST /api/auth/logout` · `POST /api/auth/password` | 是 | 改密后撤销全部令牌 |
| 身份 | `GET /api/me` · `GET /api/me/wrong` · `GET /api/me/progress` · `DELETE /api/me/data` | 是 | **学生只见自己**（F15） |
| 答疑 | `POST /api/chat`（**`fetch` 流，非 EventSource**；请求头带 `X-Model-Key`） | 是 | 事件 `seq` 单调；**无凭据 ⇒ 503 `model_unavailable`** |
| ★ 模型 | **`POST /api/model/ping`** · `GET /api/model/providers` | 是 | `ping` 校验用户凭据（避免"填错 key 后每次答疑都失败"）；`providers` 返回预置供应商（DeepSeek / Qwen / GLM + 自定义 OpenAI 兼容） |
| 刷题 | `GET /api/problems` · **`POST /api/practice/hint`** · `POST /api/practice/grade` | 是 | 判定确定性 + 线程池；**`problems` 不返回答案**；`hint` 是提示阶梯唯一入口（F6） |
| 知识 | `GET /api/knowledge/tree` · `GET /api/knowledge/formula` | 是 | 吃 DAG / 公式库（F18）；**`formula` 按名称返回唯一条目**（名称唯一性由资产校验保证） |
| 管理 | `GET /api/admin/students` · `GET /api/admin/users` · `GET /api/admin/audit` · `PATCH/DELETE /api/admin/users/{id}` · `POST /api/admin/users/import` | 是（**管理员**） | 一律写审计；`PATCH` 含 **重置密码**（见下） |

**四处端点差异必须写清，否则契约会各写各的**：

- `GET /api/admin/students` = **数据视图**，是 §5"教师可见"的落点；`GET /api/admin/users` = **账号管理**（角色 / 状态 / 锁定 / 令牌）。两者的人**是同一批**，但关注点不同，**不要合并成一个接口**。
  ★ **"数据视图"必须写成可判定的形状（2026-09-16 修正）**：管理员可**逐条查看**本机学生的**作答记录与掌握度计数**（允许排序与筛选）；**不产出任何跨学生的派生指标** —— 界面上**不得出现平均分、排名、分布、热力图**。原措辞写的是"班级统计"，而 `docs/01 §9` 把"跨用户聚合"列为**排除项** ⇒ **同一个词在两侧意思相反，边界就没有执行载体**；改为上面这句后，可以**对着界面点数**。
- `POST /api/admin/users/import` **只能建 `student` 角色，且不接受学号 / 姓名字段** —— 否则一个便利功能就能破掉 N6（`docs/01` 已记账，ADR-0002 §v2 增量 6）。
- ★ **`PATCH /api/admin/users/{id}` 含"重置密码"（2026-09-16 补）**：**强制下次登录改密**（`must_change_pw`）+ **撤销该用户全部令牌** + **写审计**；新密码由管理员经**单独渠道**告知学生。此前这一项在 ADR-0002 决策 3 里有、在 v2 接口清单里**悬空**。

**R-A 强制的字段**（所有请求体字符串字段必须有上界）★ **本表已补齐（2026-09-16）** —— 原文只有五行，而规则声称"**所有**请求体字符串字段"，**规则的范围 ⊃ 检查表**：

| 字段 | 上界 | 理由 |
|---|---|---|
| `username` | 32 | 契约正则 `^[A-Za-z0-9_.-]{3,32}$` |
| `password` | 72 字节 | bcrypt 输入上限 |
| `answer` | **200** | 旧仓 P0：无上界 ⇒ 判定被喂 100k 位数字 |
| `query` | **2000** | 答疑提问；超长直接 400 |
| `display_name` | 64 | — |
| ★ `context.text`（F1 的上下文，可含教材片段） | **4000** + **嵌套深度 ≤ 3** | ★ **比 `query` 更危险**：它是**常用路径**（F1 明确要求无上下文时显式降级），也是**最容易被塞进大对象**的参数（`{"text": "<1MB>"}`） |
| ★ `session_id` | 64 | 出现在 `hint` 与 `grade` 两处 |
| ★ `item_id` | 64 | 同上 |
| ★ `cursor` | 256，**且必须校验可解码** | 不校验就是一个**注入面** |

> ★ **"静态扫描"的实现方式必须写明**（否则门禁本身不可 review —— 这与 §9 对运行器"必须可 review"是同一条标准）：扫描**请求体模型的字段声明**（Pydantic 层），断言**每个 `str` 字段都带 `max_length`**；对正则，断言判定类正则**不含嵌套量词**（`(...)+` / `(...)*` 内部再有量词）。

### 6.2 统一错误体（`error.schema.json` —— 旧仓的缺口之一）

```json
{
  "error": {
    "code": "unauthenticated",
    "message": "未登录或登录已过期，请重新登录",
    "detail": { "field": "password", "reason": "too_short" }
  }
}
```

| 字段 | 含义 | 约束 |
|---|---|---|
| `code` | **机器读的稳定标识**（枚举，见 §6.3） | 只增不改；新增须走契约变更 |
| `message` | **给人看的中文说明** | 不含内部路径 / SQL / 堆栈 |
| `detail` | **可选**结构化补充（哪个字段错了、缺什么） | 不得放敏感值 |

**为什么要有它**：旧仓每个接口各写各的形状（有时是字符串，有时是对象，有时干脆是 500），前端只能按形状猜。**统一错误体是前端能写出一套错误处理的前提**。

### 6.3 状态码与 `code` 语义表

| HTTP | `code` | 触发条件 | 前端行为 |
|---|---|---|---|
| 400 | `invalid_argument` | 参数校验失败（含超长、格式） | 高亮字段 + 显示 `message` |
| 401 | `unauthenticated` | 无令牌 / 令牌无效 / 已过期 / 已撤销 | **清本地令牌 + 跳登录** |
| 401 | `bad_credentials` | 登录时用户名或密码不正确 | 显示提示，**不清空用户名** |
| 403 | `forbidden` | **非管理员访问 `/api/admin/*`**（角色不足） | 显示"无权访问"，**不跳登录** |
| 403 | `account_disabled` | 账号被禁用（**仅在密码验证通过之后可能出现**） | 显示"账号已停用，请联系老师" |
| 404 | `not_found` | 资源不存在，**含"存在但不属于我"的资源**（故意不区分） | 友好提示 |
| 409 | `conflict` | 用户名已存在 | 提示换一个 |
| 423 | `locked` | 连续失败过多，短时锁定（**仅在密码验证通过之后可能出现**） | 显示剩余秒数 |
| 500 | `internal_error` | 未预期错误 | 显示"服务出错"，**附 trace id** |
| 503 | `dependency_unavailable` | 检索 / 语料缓存等依赖不可用且无降级路径 | 显示"当前为降级模式" |
| ★ 503 | **`model_unavailable`** | **未配置凭据**、供应商不可达（N14） | 显示"**未配置模型凭据**"并提供 `#/settings?tab=model` 入口；**判定 / 错题本 / 进度 / 知识图谱照常可用** |
| ★ 400 | **`model_key_invalid`** | 用户凭据无效 / 被撤销 | 提示到设置页重填；**不得清本地登录令牌** |
| ★ 402 | **`model_quota_exceeded`** | 用户凭据额度不足 / 欠费 | 提示"你的模型额度不足"，并说明**费用由凭据持有人承担** |

> ★ **凭据类错误绝不能复用 401（2026-09-16 新增，本轮最容易踩的坑）**：前端收到 `401` 的既定行为是"**清本地令牌 + 跳登录**" —— 若把"模型 key 填错"也标成 401，用户会**被登出**，而真正的问题是设置页里那串 key。因此这三个 `code` **必须是独立值**（503 / 400 / 402），且 `model_key_invalid` 用 **400** 而非 401：它是**客户端可修的输入问题**，不是身份问题。

> **越权只走一条路，不再两处定义**（本轮收口）：**读他人数据 → 404**（对外看起来"不存在"，避免用状态码探测他人 ID 是否存在；**日志里记 403** 便于排查）；**403 `forbidden` 只保留"角色不足"**，即非管理员访问 `/api/admin/*`。
> ✅ **已裁定（2026-09-16，负责人）**：旧仓把"账号被禁用"与"权限不足"都归 403 且用同一段文案；**本仓分成两个 `code`**，理由是用户需要知道"这是账号问题，去找老师启用"而不是"我权限不够"。
> **已考虑并否决的替代方案**：退回单一 `forbidden`（理由是避免泄露"该账号存在且被停用"）。
> **否决依据已从"经验判断"改成一条可断言的不变量**（评审 A3 指出原表述不成立，已修）：**在密码通过之前，一切失败都返回同一个 `401 bad_credentials`，且都烧等长的时间**（`§4.1`）。因此 `403 account_disabled` 与 `423 locked` **只可能在密码验证之后出现** —— 攻击者拿不到密码就看不到这两个状态，**不构成额外的账号枚举面**。这条不变量由登录用例直接断言（见 §8）。

### 6.4 分页口径（旧仓的第二个缺口）

**统一为 cursor 分页**，不用 `offset`：

```
请求：?limit=20&cursor=<opaque>
响应：{ "items": [...], "next_cursor": "<opaque>|null" }
```

| 规则 | 值 |
|---|---|
| `limit` 默认 / 上界 | 20 / **100**（超界即 400，不静默截断） |
| `cursor` | 不透明字符串（内部是 `created_at` + `id` 的编码），**客户端不得解析** |
| 排序 | 一律 `created_at DESC, id DESC`（稳定序，避免同秒记录乱序） |

**为什么不用 offset**：问答流水与作答记录是**追加写**的表，翻页时新记录插入会让 offset 漂移 ⇒ **同一条记录被读到两次、或某条被整页跳过**。这对"错题本复习"是真实伤害。

### 6.5 SSE 帧

帧格式与 14 类事件由 `events.schema.json` 定义（A3）。本仓对**帧的两条增量要求**：

1. **每帧带 `seq`（单调递增整数）** —— 断流续传与去重的唯一依据。
2. **终帧必须显式**（`done` 或 `error`）—— 让前端能区分"跑完了"与"网断了"，否则只能靠超时猜。

## 7. 前端系统设计

### 7.1 URL 可寻址设计（N11 —— 旧仓实测返回键失效）

**规则**：**凡是有意义的界面状态，必须由 URL 表达**。顺序是"URL 是状态源，组件是它的投影"，不是反过来。

| 路由 | 表达的状态 | 为什么必须可寻址 |
|---|---|---|
| `#/login` | 登录页 | — |
| `#/home` | 首页 | — |
| `#/practice?kc=kc_bayes&item=prob_0012&hint=2` | **具体题目的具体提示层级** | "刷到第 3 步提示"要能刷新、能分享、能回退 |
| `#/wrong?kc=kc_bayes&cursor=<opaque>` | 错题本 + 知识点筛选 + 翻页位置 | 复习到一半刷新不能回到起点 |
| `#/knowledge?kc=kc_bayes&view=graph` | 知识点定位 + 视图模式 | 分享"就是这个知识点不会" |
| `#/admin?tab=students&user=usr_xxx` | 管理页标签 + 选中学生 | 管理员排查时要能把链接发给别人 |

**三条实现要求**：
① 监听 `hashchange` **与** `popstate`（旧仓只写 hash、无人监听 ⇒ 返回键只变 URL 不变视图）；
② 视图状态从 URL **单向派生**，组件不得各存一份；
③ ★ **URL 是渲染状态的来源，不是权限或计数的来源** —— `hint=2` 只决定"界面显示到第几级"，**提示次数一律以服务端 `hint_log` 为准**（F6）。手工把 `hint` 改成 2 不会让服务端认为已取过提示，也不会让解析提前出现。

### 7.2 外壳与页面注册

| 部分 | 职责 | 谁写 |
|---|---|---|
| `frontend/index.html` | 唯一 HTML；引 CSS（4 层）与 `bootstrap.js` | R1 |
| `core/` | `dom`（创建元素 / 转义）· `bus`（事件）· `store`（内存态）· `router`（**含 hashchange**）· `api`（fetch 包装 + 错误体解析）· `auth`（令牌 / 角色） | R1 |
| `components/` | 复用 UI（表格 / 卡片 / 骨架 / 空态 / 图表） | R1 |
| `features/<x>/` | `feature.json`（id / route / 标题 / 顺序）+ `index.js` + `styles.css` | **一人一页** |

**依赖方向**：`features/*` **不得互相 import**（只能经 `core/bus.js`）；`components` 不得 import `features`。

### 7.3 样式分层（**单一令牌源**）

```
styles/tokens.css       ← ★ 唯一变量源（颜色/圆角/阴影/间距/过渡）
styles/app.css          ← 外壳骨架（布局、侧栏、顶栏）
styles/components.css   ← 通用组件
styles/pages.css        ← 页面模板层（页面头/工具栏/表格/空态/骨架）
features/<x>/styles.css ← 只写该页独有样式，**禁止硬编码颜色**
```

**规则**：任何颜色 / 圆角 / 阴影**只能来自 `tokens.css`**。旧仓 `widget.css` 有 **77 处硬编码色值**（其中 13 处与 token 同值）—— 那是双形态遗留；v2 单形态下这条规则可被脚本扫描守住。

### 7.4 状态管理的边界

| 状态 | 存哪 | 为什么 |
|---|---|---|
| 令牌 | `localStorage` | 免构建、无后端渲染；XSS 风险由"不用 `innerHTML` 拼用户内容"控制 |
| 界面位置（知识点 / 题目 / 提示层级 / 翻页） | **URL** | N11：可刷新、可分享、可回退 |
| 跨页面临时态（当前 run、未提交的作答） | `core/store`（内存） | 刷新即丢是**可接受的** —— 它们本来就不该是持久状态 |
| 持久学习数据 | **只在服务端** | 单一真相；避免前后端两套数据打架 |

## 8. 失败模式与降级（一开仓就定死，不留给日后踩）

| # | 场景 | 设计行为 | 谁守（测试） |
|---|---|---|---|
| 1 | **未登录 / 令牌过期** | 401 `unauthenticated`；前端清令牌并跳登录 | 接口测试 |
| 2 | **令牌被撤销**（改密 / 禁用 / 删除） | 立即 401（**不是等 7 天**） | 接口测试 |
| 3 | **越权读他人数据** | 404（对外）· 403（日志） | 越权用例 |
| 4 | **账号禁用 / 锁定** | 403 `account_disabled` / 423 `locked`；两者**只能出现在密码验证通过之后** | 接口测试 |
| 4b | ★ **登录失败的信息量不变量** | **密码通过之前一切失败都是同一个 401 `bad_credentials`，且响应耗时同量级** —— 断言"不存在的用户"与"密码错误"返回**同一状态码 + 同一 code**，且"已禁用/已锁定账号 + 错误密码"**也不泄露**其存在 | 登录用例（枚举面回归） |
| 5 | **超长输入** | 400（有上界）；**绝不进入判定** | R-A 扫描 + 长度用例 |
| 6 | **正则灾难性回溯** | 禁嵌套量词；数字长串专项用例 | 用例（100k 数字须 < 1s） |
| 7 | **判定阻塞事件循环** | 同步 CPU 工作全部 `to_thread` | 并发健康检查（**判定压测时 `/api/health` 必须仍 < 100ms**） |
| 8 | **写库静默回滚** | 显式 `commit()`；测试读回断言 | R-B 扫描 + 读回用例 |
| 9 | **SQLite 并发写** | WAL + `busy_timeout=5000` | 并发写用例 |
| 10 | **SSE 客户端断开** | **取消图**，释放资源 | 断流用例（断开后无残留任务） |
| 11 | **SSE 网络中断** | 前端按 `seq` 续传 / 重连；不重复渲染 | 前端用例（注入重连） |

> **第 14 条为什么必须"报错退出"而不是"警告后继续"**：F19 要求 DAG 无环、F20 要求条目挂知识点。资产坏了而系统照跑，产生的是**带错误知识点标注的作答记录** —— 那些记录会污染掌握度与错题本，且事后无法区分哪些是坏的。**宁可起不来。**
> **第 15 条为什么必须是启动检测**：旧仓把"只允许单 worker"写在文档里，**代码不检测** —— 于是部署时多开一个 worker 就出现"随机丢 run / 事件串台"，而症状看起来像前端 bug。

## 9. 评测资产的存放与执行（N13 · 盲测）

A1 已定（本轮回补时同步细化）：**样例集与运行器入仓并纳入门禁（防退化）· 冻结正式集由非实现者保管、不入主仓（能力验收）**。本篇给出可执行形式：

> ★ **理由已换锚（2026-09-16）**：原文写的是"**离线、无密钥基础设施的前提下（ADR-0001），门禁无法从仓库外取题**" —— 那个前提**已不成立**（v2 联网、且用户自持凭据，理论上可以联网取题）。**结论不变，理由改成**：为一件**用一次**的验收，引入**外部托管位置 + 一套取题凭据**，成本高于收益；而"**正式集不进仓**"这条隔离要求**与能不能联网无关**。

| 资产 | 存在哪 | 谁写 | 谁执行 | 自动化 |
|---|---|---|---|---|
| **样例集**（3–5 题 + 期望结论） | **`content/eval/sample/`**（**入仓**） | 非实现者 | 本地门禁（接远端后即 CI） | ✅ 自动红灯 |
| **运行器** | `scripts/eval_verify.py --frozen-dir <dir>`（**入仓，不含任何答案**） | 任意人 | 非实现者 | — |
| **冻结正式集**（注入集 20 道 + 冻结验证集） | 主仓**之外**（非实现者本机） | 非实现者 | 非实现者 | ❌ 人工门禁 |
| **期望判据表** | 与正式集同处，**不入主仓** | 非实现者 | — | — |

**为什么把"评分脚本"拆成"运行器 + 期望判据表"**：运行器本身**必须可 review**（否则没法确认它真的在数命中，而不是在数"没报错"）。把**答案**移出仓库、把**机制**留在仓库，两个目的同时达成。（该细化已同步回 `docs/01` 的 N13 与附录 B.2。）

### 9.1 ★ 注入集口径（本轮定死 —— 否则这个门禁会平凡通过）

| 项 | 定义 | 为什么必须写死 |
|---|---|---|
| **注入物** | **系统错解**：一道题 + **一个已知错误的解答** | **不是学生错解**。学生答错本来就该被判错，"拦住"便无从体现 |
| **注入点** | **验证链的输入**（**函数级**、确定性、可批量） | 走 `/practice/grade` 是错的：那条链路上任何错答案都会被判为错，**门禁平凡通过** —— 正是 N1 自己警告的"可以被满足而毫无效果" |
| **断言** | 该解答**被标注 `uncertain` / 存疑，或级别被降**（`§4.2-4` 的降级出口） | 与 §4.2 的验证分支一一对应，无歧义 |
| **分层** | **函数级 20 道**（盲测、人工门禁）+ **端到端 3–5 道**（样例集、进门禁） | 函数级保证覆盖率与确定性；端到端保证"这条链真的接上了" |

**执行时机**：**阶段门 C 的出口条件之一**。执行记录（日期 / 执行人 / `content_rev` / 逐类命中数 / 结论）留档，**结论写进 `docs/06`**。

### 11.2 诚实缺口（本篇现在缺什么）

1. ~~题库与题型的真实规模未定~~ → **已定**（F20 四类下界：题库 ≥ 30 道 · DAG ≥ 40 节点 ≥ 5 章 · 错因库 ≥ 40 · 题型 ≥ 15；长期目标题库 ≥ 100 道另记）。**但仍缺"谁产出、何时产出"** —— 那是 `docs/05` 的 R-C 责任人表，不属本篇。
2. **`student_user` 的字段级定义不在本篇**：沿用已落地实现；机器可读定义在 A3 的契约里。本篇只记增量（`asset_version` · `correct` 可空 · `grader` 新取值 · `created_at` 补记）与**删除**（`deleted`）。
