# ADR-0001 · 前端采用免构建 ESM，而非 Next.js

- **状态**：已接受（2026-09-06 于旧仓作出；2026-09-16 **搬运至 v2 并重新评估，结论不变**）
- **决策人**：R1（架构）/ R4（前端）
- **相关**：`docs/01-需求分析` N4 · `docs/02-系统设计` §1.2 §7 · `docs/03-架构总览`· ADR-0003

> **搬运说明**：本文从旧仓 `ProbCrew/docs/adr/0001` 搬运，**决策与理由原样保留**（历史记录不得改写）。

---

## 背景

团队在 `reproduce/math-tutor` 与 `reproduce/eduagents` 中已有 Next.js 复现经验，直觉上会倾向继续用 Next.js。但本项目有三个硬约束：

1. **要建立在既有 8 个自包含 HTML 动画之上**。这些动画是 vanilla JS + Canvas，零依赖，可以直接双击打开。引入打包器会把它们变成"构建产物"，损失可单独分发、可离线、可嵌入数字教材的特性。
2. **需要离线 / 内网演示**。答辩现场网络不可控，构建链越长，出问题的环节越多。
3. **多人并行开发，且前端不是所有人的强项**。构建工具、依赖版本、`node_modules` 会迅速成为协作摩擦源（"我这边跑不起来"）。

同时，本项目的 UI 复杂度是可控的：页面数少、无 SSR/SEO 需求、无复杂状态管理。

---

## 决策

前端采用**原生 ESM + 动态 import**，不引入打包器。

具体做法：

- 浏览器直接加载 `/app/bootstrap.js`（`<script type="module">`）。
- feature 通过**动态 import** 加载：`await import('./features/${dir}/index.js')`，目录清单由 `scripts/gen_registry.py` 扫描 `feature.json` 生成。
- **依赖控制在零**：KaTeX 用 `vendor/katex/`（本地，约 1.6MB）；Markdown 与图表都是自写的小实现。
- 公式渲染、Canvas 图表全部由浏览器原生能力完成。
- 由 FastAPI 的 `StaticFiles` 托管整个 `frontend/`，保证与后端**同源**。

---

## 后果

**正面**

- 零安装、零构建：起来就能改，改完刷新浏览器即生效（无 HMR，但改一两个文件时刷新足够快）。
- 交付方式与自包含静态资源一致 —— 没有"构建产物"与"源码"两套东西。
- 新人上手成本极低：会写 HTML/CSS/JS 就能贡献页面。
- 离线可用：断网、内网答辩都不受影响。
- 没有 `node_modules`，仓库轻、门禁快。

**负面**

- **没有 TypeScript 类型检查**。缓解：以 `contracts/*.schema.json` 为契约，由门禁脚本做运行时校验；内核行为由 `backend/tests` 覆盖。
- **没有 HMR**，改样式需手动刷新。缓解：浏览器 DevTools 里可直接改 CSS 调试。
- **依赖增长后模块图会变复杂**。缓解：**禁止 feature 之间互相 import**（只走 `core/bus.js`），共享代码必须放 `components/` 或 `core/`。
- **无法做 SSR/SEO**。本项目是教学工具，不需要。

## 被否决的备选方案

| 方案 | 否决理由 |
|---|---|
| Next.js（复用复现经验） | 构建链重、`node_modules` 摩擦大、与静态资源托管方式不一致；本项目不需要 SSR |
| Vite + Vue/React | 比 Next.js 轻，但仍引入构建步骤与依赖；页面规模小，收益不明显 |
| 单文件大 HTML（沿用旧原型） | 单文件千余行无法多人并行 —— 这正是本项目要解决的问题 |

---

## 何时重新评估

满足**任一**条件时，重新讨论是否迁移到 Vite / Next.js：

1. `frontend/features/` 下模块数 **> 25**；
2. 出现真实的 SSR / SEO / 公开门户需求；
3. 需要 TypeScript 强类型来防止线上事故（例如契约字段被误用已造成 ≥ 3 次故障）；
4. 需要复杂状态管理或大量第三方 UI 组件。

迁移成本预估：页面逻辑本身是标准 ESM，`core/` 与 `components/` 可直接复用，主要工作量在把 `h()` 调用改为 JSX、把 `feature.json` 改为路由配置 —— 约 3–5 人日。

## §v2 重新评估（2026-09-16）

搬运到 v2 时逐条核对了本 ADR 的三条前提。**结论不变：继续免构建。**

| 旧前提 | v2 是否成立 | 说明 |
|---|---|---|
| ① 建立在"既有 8 个自包含 HTML 动画"之上 | **部分** | v2 的动画库（F12）仍在范围内，但**不再依赖"8 个自包含 HTML 文件可双击打开"这个交付方式**。因此这条理由**弱化**了 |
| ② 需要离线 / 内网演示 | ❌ **★ 前提已不成立（2026-09-16 修正）** | **同上一条修正**：v2 的需求口径改为**用户自持凭据 + 学习资源联网可达**（`docs/01` N14 / N15），**"数据不出校 / 离线可跑"已废弃**（N3 废弃、N4 收窄）。因此**这条理由不再成立**，且**不能再被引用** —— 见下"一次被证伪的前提" |
| ③ 多人并行、前端非强项 | **仍成立** | 四人小组，构建工具的摩擦系数不变 |
| UI 复杂度可控 | **仍成立** | v2 页面更少（主站单一形态），复杂度更低 |
| **★ 零依赖（v2 新增理由）** | **成立** | 免构建的真正价值在 v2 锚在这里：**vendor 本地化 + 零 npm 依赖**，因此不引 Markdown / 图表 / 净化库，也不引构建链 |
| ★ **正文第 32 行的 `scripts/gen_registry.py`（扫描 `feature.json` 生成目录清单）** | ❌ **不继承** | `docs/03 §6.2` 已定"**v2 不做代码生成**"，原则二为"**显式优于隐式**（不靠扫描目录自动发现）"。前端注册表因此**必须是显式的**（`docs/03 §5`）。★ **正文第 31 行的 `/app/bootstrap.js` 亦已过时**：v2 是 `frontend/bootstrap.js`（`docs/03 §2`）。本文正文保留不改（ADR 是历史记录），**以本表为准** |

**另外一个理由在 v2 变强了**：ADR-0003 决定放弃注入式探针。旧仓之所以需要"纯 Python 共享内核打包器"这类复杂机制，正是因为要同时兼容 ESM 与经典脚本两种形态。**单形态之下，免构建的代价进一步下降**。

### ★ 一次被证伪的前提（必须记下来）

本 ADR 的**理由 ②**（离线 / 内网演示）在 v2 被**证伪**了：需求方于 2026-09-16 明确"不是离线或局域网可跑，而是允许用户自接 key 的 agent 助手"。

**这件事的教训比结论重要**：我在把本 ADR 搬进 v2 时，曾把它写成"**★ 更强**：已是 N3 + N4 两条 MUST"。**那是错的** —— 我把一条**当时恰好写在文档里**的前提，当成了**不会变的需求**。而 N3/N4 当时确实存在，所以"更强"在**当时的文档内部**是自洽的；错在于**没有区分"需求文档写了"与"需求不会变"**。

**记账**：免构建的**决策**不变，但它现在**只剩一条半理由**（③ 多人并行 + 零依赖），因此"何时重新评估"的门槛应当更敏感 —— 若将来团队变大、或需要引入第三方 UI 库，本 ADR 的结论会**比原来更容易被推翻**。

**顺带记录的旧仓缺陷**：旧仓本 ADR 的"相关"一节写着 `ADR-0002（动画文件只读、靠 manifest 接入）`，但旧仓的 ADR-0002 实际是"账号体系与身份口径" —— **引用错位**。搬运时未继承该错误；v2 的 ADR-0002 确为账号体系。
